## Why a SPARQL backend

- Your project prefers to keep its geodata as **RDF** (GeoSPARQL) rather than in a relational database.
- The geodata already lives in a **triple store** or a public SPARQL endpoint.
- You want a lightweight, read-only demo without PostgreSQL.

## How it works

The Metapolis app needs only one thing from its backend: the result of the `all_buildings` query (`building_id`, `name`, `function`, `wkt`) returned by the `metapolis` repository.

- With **PostGIS**, the [SQL Sail](PostGIS-and-SQL-Sail) produces it from the `metapolis.buildings` table.
- With a **SPARQL backend**, the same shape is stored as plain triples (`rs_sql_sail:hasQueryId "all_buildings"`, `metapolis_sql:name`, …). The `metapolis` repository is a plain SPARQL repository that forwards the queries to the endpoint.

Because the triples mimic the SQL Sail output, the forms, the map, the Knowledge Patterns and the Ephedra federation work **unchanged**: only `config/repositories/metapolis.ttl` differs.

```
Metapolis forms & map ──▶ Ephedra ──SERVICE <…federation#metapolis>──▶ "metapolis" repository (SPARQLRepository)
                                                                               │  SPARQL (HTTP)
                                                                               ▼
                                                               QLever / your SPARQL endpoint
```

## QLever

[QLever](https://github.com/ad-freiburg/qlever) is a fast SPARQL engine. `metapolis_setup/metapolis-qlever/` runs it in Docker, loaded with the same 8 sample buildings as the PostGIS setup, with the same IDs.

```
metapolis_setup/metapolis-qlever/
├── docker-compose.yml   # QLever SPARQL endpoint
├── .env.template        # Copy to .env
└── data/buildings.ttl   # Sample buildings as GeoSPARQL + Metapolis triples
```

### Quick start

With `setup.sh`, from the `metapolis` app repository:

```bash
./setup.sh --backend qlever                                    # ResearchSpace on the host
./setup.sh --backend qlever --data-host host.docker.internal   # ResearchSpace in Docker
```

This clones `metapolis_setup` if needed, creates `metapolis-qlever/.env`, starts the `metapolis-qlever` container on port `7001`, waits until it is healthy, checks that it returns buildings, and writes `config/repositories/metapolis.ttl`.

Or by hand, from `metapolis_setup`:

```bash
cd metapolis-qlever
cp .env.template .env
docker compose up -d
```

Then write the repository configuration yourself (below) and continue with the rest of the installation: add the app, restart ResearchSpace, add `metapolis` to the Ephedra federation and import the configuration, as described in [Installation and Setup](Installation-and-Setup#step-4-add-metapolis-to-the-ephedra-federation). With `setup.sh`:

```bash
./setup.sh --backend qlever --rs-url http://localhost:10214
```

and then import `Metapolis_KP.trig` by hand in **System Settings → Knowledge Patterns**.

### Environment variables

| Variable | Default | Description |
|---|---|---|
| `QLEVER_PORT` | `7001` | Port exposed on the host |
| `QLEVER_IMAGE` | `adfreiburg/qlever:latest` | Docker image |
| `CONTAINER_NAME` | `metapolis-qlever` | Docker container name |
| `QLEVER_MEMORY` | `1G` | Memory for query processing |
| `QLEVER_ACCESS_TOKEN` | `metapolis` | Token for QLever's admin commands (cache clearing, updates). Change it if the port is reachable from other machines |

### Repository configuration

`setup.sh` writes this `config/repositories/metapolis.ttl` (with `host.docker.internal` instead of `localhost` if you passed `--data-host`):

```turtle
# Generated by setup.sh (backend: qlever). Re-run setup.sh to change it.
@prefix repo: <http://www.openrdf.org/config/repository#> .
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix sparqlr: <http://www.openrdf.org/config/repository/sparql#> .

[] a repo:Repository ;
  repo:repositoryID "metapolis" ;
  rdfs:label "Metapolis geodata (SPARQL endpoint)" ;
  repo:repositoryImpl [
    repo:repositoryType "researchspace:SPARQLRepository" ;
    sparqlr:query-endpoint <http://localhost:7001>
  ] .
```

The repository ID stays `metapolis`, so the federation member and all templates keep working. Restart ResearchSpace after changing this file.

> ⚠️ `metapolis.ttl` is tracked by git. Do not commit a version that points to your local endpoint unless you mean to.

### Data

Every `.ttl` file in `data/` is loaded. The index is **rebuilt from `data/*.ttl` each time the container starts** (a few seconds for the sample data), so the endpoint always reflects the files.

`data/buildings.ttl` is generated from `metapolis-db/init-scripts/03-insert-sample-buildings.sql`, so both backends serve the same buildings with the same IDs. Each feature is described twice:

- as **GeoSPARQL** (`geo:Feature`, `geo:hasGeometry`, `geo:asWKT`) plus Metapolis properties: the "real" data, usable by standard GIS and Linked Data tools;
- with the **`metapolis_sql:*` properties** used by the Metapolis app queries. PostGIS answers these through the SQL Sail; RDF backends answer them from these triples.

```turtle
@prefix rdfs: <http://www.w3.org/2000/01/rdf-schema#> .
@prefix geo: <http://www.opengis.net/ont/geosparql#> .
@prefix metapolis_ontology: <http://metapolis.com#> .
@prefix feature: <http://metapolis.com/resource/feature/> .
@prefix geometry: <http://metapolis.com/resource/geometry/> .
@prefix rs_sql_sail: <http://www.researchspace.org/resource/system/sql#> .
@prefix metapolis_sql: <http://www.researchspace.org/resource/system/service/metapolis_sql#> .

feature:1 a geo:Feature ;
  rdfs:label "Palazzo Vecchio" ;
  metapolis_ontology:function "Government" ;
  metapolis_ontology:start_year 1314 ;
  geo:hasGeometry geometry:1 ;
  rs_sql_sail:hasQueryId "all_buildings" ;
  metapolis_sql:building_id 1 ;
  metapolis_sql:name "Palazzo Vecchio" ;
  metapolis_sql:function "Government" ;
  metapolis_sql:wkt "POLYGON((11.2558 43.7696, 11.2562 43.7696, 11.2562 43.7700, 11.2558 43.7700, 11.2558 43.7696))" .

geometry:1 a geo:Geometry ;
  geo:asWKT "POLYGON((11.2558 43.7696, 11.2562 43.7696, 11.2562 43.7700, 11.2558 43.7700, 11.2558 43.7696))"^^geo:wktLiteral .
```

### Adding or changing buildings

1. Edit `data/buildings.ttl`, or add another `.ttl` file in `data/`, following the same pattern.
2. Use the feature IRI `http://metapolis.com/resource/feature/<building_id>`, with a `building_id` that is unique across all files. Buildings in Metapolis are linked to features through this IRI.
3. Keep the WKT in **WGS84 (EPSG:4326)**, longitude first, and identical in `metapolis_sql:wkt` and `geo:asWKT`.
4. Restart the container to rebuild the index:

   ```bash
   docker compose restart
   ```

The QLever endpoint is **read-only** from ResearchSpace: geometries are edited in the `.ttl` files, not in QGIS. To go from QGIS to RDF, export the layer (e.g. to GeoJSON or CSV with WKT) and convert it to the pattern above.

### Testing the endpoint

From the host:

```bash
curl -s http://localhost:7001 -H 'Accept: text/csv' \
  --data-urlencode 'query=SELECT ?name WHERE { ?f <http://www.w3.org/2000/01/rdf-schema#label> ?name }'
```

The query `setup.sh` uses to check a SPARQL backend (it should return 8 with the sample data):

```sparql
PREFIX rs_sql_sail: <http://www.researchspace.org/resource/system/sql#>
PREFIX metapolis_sql: <http://www.researchspace.org/resource/system/service/metapolis_sql#>

SELECT (COUNT(*) AS ?n) WHERE {
  ?s rs_sql_sail:hasQueryId "all_buildings" ;
     metapolis_sql:building_id ?building_id ; metapolis_sql:name ?name ;
     metapolis_sql:function ?function ; metapolis_sql:wkt ?wkt .
}
```

In ResearchSpace, run the usual `all_buildings` checks on the **metapolis** and **ephedra** repositories ([Installation, Steps 3 and 4](Installation-and-Setup#step-3-point-the-app-at-the-database)).

## Custom SPARQL endpoints

You can point Metapolis at any SPARQL endpoint that holds your geodata:

```bash
./setup.sh --backend sparql --endpoint https://example.org/sparql
```

The script checks that the endpoint answers and warns if it does not contain data in the shape Metapolis expects (it writes the configuration anyway). The repository configuration is the same as for QLever, with your URL as `sparqlr:query-endpoint`.

### Expected triples

For each feature, the endpoint must contain:

```turtle
@prefix geo:           <http://www.opengis.net/ont/geosparql#> .
@prefix rdfs:          <http://www.w3.org/2000/01/rdf-schema#> .
@prefix rs_sql_sail:   <http://www.researchspace.org/resource/system/sql#> .
@prefix metapolis_sql: <http://www.researchspace.org/resource/system/service/metapolis_sql#> .

<http://metapolis.com/resource/feature/1>
    # Required: what the Metapolis forms and map query
    rs_sql_sail:hasQueryId    "all_buildings" ;
    metapolis_sql:building_id 1 ;
    metapolis_sql:name        "Palazzo Vecchio" ;
    metapolis_sql:function    "Government" ;
    metapolis_sql:wkt         "POLYGON((11.2558 43.7696, ...))" ;
    # Recommended: standard GeoSPARQL, for other tools
    a geo:Feature ;
    rdfs:label "Palazzo Vecchio" ;
    geo:hasGeometry <http://metapolis.com/resource/geometry/1> .

<http://metapolis.com/resource/geometry/1>
    a geo:Geometry ;
    geo:asWKT "POLYGON((11.2558 43.7696, ...))"^^geo:wktLiteral .
```

- Use the feature IRI `http://metapolis.com/resource/feature/<building_id>`.
- `metapolis-qlever/data/buildings.ttl` in `metapolis_setup` is a complete example.
- If your data uses another model, add the `metapolis_sql:*` triples with a SPARQL `INSERT`, or generate them with a `CONSTRUCT` query, for example from GeoSPARQL data:

  ```sparql
  PREFIX geo: <http://www.opengis.net/ont/geosparql#>
  PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
  PREFIX xsd: <http://www.w3.org/2001/XMLSchema#>
  PREFIX metapolis_ontology: <http://metapolis.com#>
  PREFIX rs_sql_sail: <http://www.researchspace.org/resource/system/sql#>
  PREFIX metapolis_sql: <http://www.researchspace.org/resource/system/service/metapolis_sql#>

  INSERT {
    ?f rs_sql_sail:hasQueryId "all_buildings" ;
       metapolis_sql:building_id ?id ;
       metapolis_sql:name ?name ;
       metapolis_sql:function ?function ;
       metapolis_sql:wkt ?wkt .
  } WHERE {
    ?f a geo:Feature ; rdfs:label ?name ;
       metapolis_ontology:function ?function ;
       geo:hasGeometry/geo:asWKT ?geomWkt .
    BIND(STR(?geomWkt) AS ?wkt)
    BIND(xsd:integer(STRAFTER(STR(?f), "http://metapolis.com/resource/feature/")) AS ?id)
  }
  ```

### Endpoints that need a login

Edit `config/repositories/metapolis.ttl` after running the script and use the basic-auth repository type:

```turtle
@prefix mph: <http://www.researchspace.org/resource/system/repository#> .

[] a repo:Repository ;
  repo:repositoryID "metapolis" ;
  repo:repositoryImpl [
    repo:repositoryType "researchspace:SPARQLBasicAuthRepository" ;
    sparqlr:query-endpoint <https://example.org/sparql> ;
    mph:username "user" ;
    mph:password "secret"
  ] .
```

Restart ResearchSpace after any change to `metapolis.ttl`.

## Differences from PostGIS

| | PostGIS (SQL Sail) | QLever / SPARQL |
|---|---|---|
| `all_buildings` | ✅ | ✅ (stored as triples) |
| Other predefined queries (`buildings_by_function`, `buildings_in_bbox`, `buildings_near_duomo`, …) | ✅ | ❌ – they exist only in the SQL service. Query the GeoSPARQL data directly instead (e.g. `FILTER`, or GeoSPARQL functions if your engine supports them) |
| `?s` in `all_buildings` | A blank node per SQL row | The feature IRI |
| Editing geometries | QGIS or any GIS writing to PostGIS | Edit the RDF (`.ttl` files for QLever) |
| Writes from ResearchSpace | – | Read-only |
| Forms, map, Knowledge Patterns, federation | Unchanged | Unchanged |

The map page queries the `metapolis` repository directly with `all_buildings`, so it works with either backend. If you build your own map pages on a SPARQL backend, you can select the GeoSPARQL properties instead (see the [Map Component Guide](Map-Component-Guide)).

## Switching back to PostGIS

```bash
./setup.sh --backend postgis
```

This starts PostGIS and rewrites `metapolis.ttl` with the SQL Sail configuration. Restart ResearchSpace. Stop QLever with `docker compose down` in `metapolis-qlever/` if you no longer need it.

## Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| `setup.sh` says "QLever is up but returns no buildings" | The `.ttl` files did not load. Check `docker logs metapolis-qlever` for parse errors |
| `all_buildings` works with `curl` but not from ResearchSpace | ResearchSpace runs in Docker and `localhost` points to its own container: re-run with `--data-host host.docker.internal` |
| A new building does not appear | The container was not restarted after editing `data/`, or the feature lacks one of the required `metapolis_sql:*` triples |
| A predefined query other than `all_buildings` returns nothing | Expected: it only exists with PostGIS |
| The custom endpoint returns HTTP 401 | Use `researchspace:SPARQLBasicAuthRepository` with credentials |
